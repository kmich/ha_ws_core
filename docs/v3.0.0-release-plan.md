**Status: implemented on `feature/v3-decision-engine` (see `CHANGELOG.md` for final shipped behavior and release notes).**

Prepared 17 November 2026, revised after an independent review of the first draft. This document combines the two reviews into one plan. It authorizes no code changes, migrations, deployment, release or publication. Implementation starts only after the user approves the plan.

## Release decision

Deliver **two releases in order**:

1. **v2.14.0 - correctness and reliability.** The confirmed defects that can be fixed without changing learned-model definitions or stored schemas. Small, reviewable, shipped as soon as its gates pass.
2. **v3.0.0 - decision engine foundation.** Learning-state migration, scientific consistency, shared quality/forecast-validity contract, menu-based configuration and the **weather windows** feature. Optional v3.0.0 beta/RC builds validate the combined release before stable publication.

If the maintainer prefers a single release, the fallback is one v3.0.0 with an internal RC checkpoint after milestone M2, and the 2.14 scope below ships inside it. That trade-off is the maintainer's call; this plan recommends two releases.

Product promise for v3.0.0: **"Your station helps you decide when to act, explains why, and tells you when the data is insufficient."**

| Priority | Work package | Required result |
|---|---|---|
| P1 | Learning feature consistency | (1) Add `cloud_deficit`, `solar_ok`, `last_day_clearness` and `last_day_clearness_ok` to the replay-masked features so absent historical solar data no longer trains the standardizer as real zeros; their replay gradient is already zero, but prove replay/live equivalence with a test. (2) Align `dp_3h`: live input is `least_squares_pressure_trend`, hPa per 3 hours, while replay uses hPa per hour; pick one canonical unit and apply it to both |
| P1 | Automatic pressure calibration safeguards | Complete the like-for-like pressure basis (surface versus sea-level path, validated elevation) and preserve manual offsets. The immediate elevation fix ships in A1 |

**Learning-state migration is part of the A2 fix, and it reuses the existing history-method mechanism.**

- Reuse `PATTERN_HISTORY_METHOD`, the targets-replayed-before check and the 2.13.17 "forget and relearn" flow in `pattern_runtime.py` instead of inventing a new migration framework.
- A method bump alone is not enough: the stale check only re-queues history entries whose status is not "ok", and the 2.13.17 reset is keyed to a separate units-method constant. Add an analogous features-method constant and a reset scoped to the affected features (standardizer slot and weight) inside each model, not to whole targets.
- **Per-feature reset.** For the four masked solar features (`cloud_deficit`, `solar_ok`, `last_day_clearness`, `last_day_clearness_ok`) and for `dp_3h`, reset the standardizer slot (n, mean, var) and that feature's weight in every model that uses it: `dp_3h` is used by rain, frost, gust and storm; the solar features by rain, heat, storm and frost. Weights for those features were learned against a corrupted or mixed-unit scale, so keeping them while resetting the slot would be inconsistent. All other weights, base rates, conditional rates and standardizer slots are kept.
- **Validate before choosing per-feature over per-target.** Other weights co-adapted with the reset ones. Compare a per-feature reset against a per-target relearn on replayed history (time-ordered, held-out) and fall back to per-target relearn for any target where the per-feature result is measurably worse.
- Relearning uses recorder history, which cannot supply wind direction, the storm distance filter or the solar features. State this limit in the changelog and diagnostics, and expect the affected models to show a collecting or lower-maturity state for a while.
- Re-replaying on top of weights trained on the wrong scale would double-train them, so replay only after the reset.
- Preserve unrelated accumulated history and model state, and show the reason for any temporary learning state.
- If the migration adds no new storage schema, downgrade tolerance is retained; verify this with a test rather than assuming it.
- Do not merely change live inputs while retaining incompatible trained weights.

**Pressure comparison must be evidence-based.** Open-Meteo normally applies elevation downscaling; do not assume it returns unadjusted coarse-grid surface pressure. Validate supplied/returned elevation and compare like-for-like pressure. If using sea-level pressure, test the reduction and correction path rather than treating a sea-level difference as a station-pressure offset. Regional-model disagreement alone is insufficient evidence that a local instrument needs recalibration.

## Scope B - scientific consistency (v3.0.0)

Each item gates only the features that use it. Items not used by weather windows run in parallel and must not block the windows milestone; they gate the v3.1 features that need them.

| Item | Needed by weather windows? |
|---|---|
| Daily-average radiation/energy separated from instantaneous irradiance; matching periods and units in net radiation, explicit night assumption and quality label | **No.** Windows do not use irradiance (see scope C); gates ET0 and water balance |
| Separate current temperature departure from daily-mean anomaly (the 30-day window fix itself ships in A1) | No |
| Pressure trend units consistent across formulas, entity metadata, stored history, thresholds and learning; timestamp-aware gaps. Known case: the live trend is hPa per 3 h under a key named hPa per hour, while pattern replay uses hPa per hour | No for windows (they do not use it); learning uses it, so it ships with A2 |
| Anemometer-height configuration for ET0 (existing default preserved) | No (gates water balance) |
| Soil capacity and fire-weather drought assumptions made explicit; no uncalibrated relative percentage presented as volumetric field capacity | No (gates water balance) |
| Lux-factor learning audit against horizontal irradiance and valid clear-sky conditions; keep the explicitly estimated fallback until the learned alternative passes validation | No |
| Wet-bulb/globe-temperature validity ranges and approximation labels; authoritative reference cases before changing formulas | No (gates ventilation) |

Do not change rain-blend weighting or seasonal normalization merely because another choice looks stronger. Evaluate these with time-ordered data and baselines. Calibration curves, forecast skill and data quality are different concepts; the UI must not conflate them.

## Scope C - new user-facing capability (v3.0.0): weather windows

Find intervals in the **next 24 hours** that satisfy a profile's limits and minimum duration.

Initial profiles:

- **Outdoor drying:** rain probability/amount, humidity or drying potential, temperature, wind/gust and optional daylight requirements.
- **Garden work:** configurable rain, temperature, gust and daylight limits.
- **Custom profile:** the same supported inputs with user-defined thresholds and required duration.

**Input decision (made now, not at profile design time).** None of the seven forecast providers returns hourly solar irradiance; the normalized hourly schema in `providers/base.py` carries `temp_c`, `apparent_temp_c`, `dewpoint_c`, `precip_prob`, `precip_mm`, `weathercode`, `wind_kmh`, `gust_kmh`, `humidity` and `cloud_cover`. Future suitability is therefore computed from hourly temperature, humidity/dew point (vapor pressure deficit), wind and gust, rain probability and amount, cloud cover, and local solar elevation above the horizon. Cloud cover is a proxy for sunshine and must be labeled as such in the reason codes. This fully decouples M4 from scope B radiation work. Provider-supplied shortwave radiation (for example from Open-Meteo) is a possible later addition, not a v3.0 dependency.

The hourly contract is "up to 24 entries", so a window that reaches the end of the data cannot be fully assessed. Mark such windows as horizon-truncated instead of presenting an open-ended suitable interval.

Return the next suitable interval and a structured explanation of accepted/rejected intervals. Distinguish observed conditions now from predicted suitability later. Never treat a missing forecast variable as zero or safe.

Pattern Forecast's 1/3/6-hour event probabilities are not per-hour probabilities. Use them only where event definition and horizon match, or as separately identified advisory information; do not fabricate an hourly probability series. Start with provider hourly forecasts and live observations, then integrate local learning where validated.

Do not promise all providers have every needed variable or 24 hours of coverage. **Deliver a provider capability matrix** (hourly coverage, variables, units, update cadence per provider) as an M3 output, and publish the actual assessable horizon. Offline operation can retain current local advice while future windows remain unavailable.

Deliverables:

- `ws_core.get_weather_windows` read-only response action (`SupportsResponse.ONLY`).
- Profile status, next-start and next-end entities. Next-start and next-end are sensors with `device_class=SensorDeviceClass.TIMESTAMP`, returning timezone-aware `datetime` values and unknown when no window exists, so the automation blueprint can use `platform: time` with `at:` set to the entity (and `offset` for lead time). **Entity budget:** entities are created only for profiles the user enables; no profile entities by default.
- Stable reason codes and profile identifiers.
- One working dashboard view and automation blueprint.
- A calendar entity is optional polish, not a stable-release dependency.

### Common result contract and summary action

Use a common result contract containing station/profile identity and evaluation timestamp, result status and stable reason codes, input sources and observation ages, forecast valid interval and coverage, missing inputs, assumptions and quality limitations, and local-model maturity (separately from forecast probability).

Add `ws_core.get_station_summary` (`SupportsResponse.ONLY`). **Extend the existing `export_learning_state` service** rather than adding a parallel action, and register it with `SupportsResponse.OPTIONAL`, which keeps existing calls working. Today it only writes the state to the INFO log.

- Return a response keyed by entry ID.
- Default to a compact summary; the full state (every climatology day and all pattern-model data) is large and would be stored in automation traces. Offer an explicit option for full model data.
- Remove the INFO log of the full state, or lower it to DEBUG.
- Test that the response is JSON-serializable.

Keep summaries deterministic, return detailed interval data on demand rather than in sensor states, and validate unknown targets.

## Scope D - configuration and runtime support (v3.0.0)

- **Extend the existing menu pattern** (already used for rooms) to the main options flow: menus for sources, forecasts, rooms, decision profiles, thresholds, uploads and diagnostics.
- Apply safe threshold/display/profile changes without rebuilding the integration. Maintain an explicit table of changes requiring reload or targeted model invalidation; source remapping and provider changes may still reload.
- Coalesce bursts of source updates into a bounded refresh. Benchmark a short delay rather than fixing one arbitrarily. Preserve prompt hazard handling (hazard sources bypass the delay) and keep accumulation/learning sample cadence independent of packet frequency. Lifecycle rules:
  - Keep the debounce timer handle in a dedicated attribute, not in `_unsubs`, so rescheduling does not grow the list.
  - When the 60 s `_handle_tick` (`sample=True`) runs while a source-change refresh (`sample=False`) is pending, the tick cancels the pending refresh, since it computes from the latest values anyway.
  - `async_stop()` cancels any pending refresh so a coalesced callback cannot fire after `async_unload_entry`. If platform unload fails, the coordinator is not stopped (see the A1 unload fix), so the pending refresh is left alone.
- Propagate input quality by dependency. Stale wind should affect wind-dependent outputs, not invalidate otherwise valid humidity calculations.
- Extract forecast cache/scheduling, source quality and decision evaluation into focused modules. Move other subsystems only when necessary for correctness or testing.
- Avoid a wholesale coordinator rewrite and a wholesale device regrouping.

## Breaking and user-visible changes

To be finalized in the changelog; the plan commits to listing each of these explicitly.

**v2.14.0**

- Soil moisture: ambiguous probes keep current values and a Repairs prompt asks for the unit; explicit units now take effect.
- Expired cloud forecasts stop influencing the rain estimate; forecast sensors may show local-only/degraded state instead of old predictions.
- Pirate Weather precipitation values change (unit and phase correction).
- Freeze-threshold editing in imperial/override setups now round-trips correctly.
- `sensor.ws_climatology_30d`, its attributes and the 30-day anomaly sensors now use a true 30-day window instead of up to 90 days, so their values change.
- Hourly forecast rows outside the 0-2 hour window no longer receive current local readings.
- If auto-calibration is enabled, the stored calibration-bias average is reset once and pressure samples with a mismatched reference elevation are ignored; a previously applied pressure offset is left as is.
- Possible minimum HA version change (see baseline).

**v3.0.0**

- Pattern Forecast: the `dp_3h` and four solar-feature standardizer slots and their weights are reset and relearned from history inside the affected models (rain, frost, gust, storm for `dp_3h`; all five targets for at least one solar feature); other learned state is preserved. This is a real loss of part of the current learning, see "Data retention". Temporary learning state is shown with its reason.
- Pressure-calibration suggestions change.
- Downgrade: if the migration adds no new storage schema, downgrade remains tolerated; if any schema version changes, downgrade is not supported. State which case applies, back up relevant storage before migration, and document rollback limits.
- Pressure-trend and other scientific outputs change where scope B corrects them.

## Data retention and migration guarantees

What the plan commits to, and what it does not, for users who upgrade. This section is the source for the changelog wording.

**Kept in both releases**

- Station configuration, source mappings, entity IDs and unique IDs, user names and customizations.
- Recorder history of every entity.
- Manual calibration offsets and offsets already applied by auto-calibration.
- Rain baselines, daily extremes and accumulated daily records, including the stored climatology days (only which days the 30-day sensors read changes).
- Learned state outside Pattern Forecast: solar lux factor, forecast skill outcomes, dry/heat/frost streaks.
- Soil moisture values for ambiguous probes (a Repairs prompt only).

**Not kept, by release**

| Release | Reset or recomputed | Reason | Recovery |
|---|---|---|---|
| v2.14.0 | If auto-calibration is on: the stored temperature, humidity and pressure bias averages (one time) | Earlier samples compared against the wrong reference elevation | Rebuilds from the next hourly samples |
| v3.0.0 | Pattern Forecast: standardizer slot and weight for `dp_3h` (rain, frost, gust, storm) and for the four solar features (rain, heat, storm, frost) | Training and live inputs used different units or corrupted scaling | Relearned from recorder history, then from live data; limited by what the recorder can supply |

**Guarantees**

- No release deletes or rewrites unrelated stored data; the migration tests assert this byte for byte.
- Before any v3.0.0 migration, relevant storage is backed up; the changelog states what is reset, why and how long relearning takes.
- If any storage schema version changes, downgrade after migration is not supported; if none does, downgrade tolerance is tested and stated.
- The plan does not promise that relearned models match the current ones; any claim of improved skill requires held-out, time-ordered evaluation.

## Release gates

### Common to both releases

- Full tests on **HA 2026.11.2 / Python >=3.14.2 on Linux** with matching HA test fixtures; verify the installed HA version in CI.
- Compatibility checks for the declared minimum HA version.
- Real setup/unload/reload, failed-unload and cancellation tests; no late task publishes into a removed entry.
- Unit round-trip tests for metric/imperial/overrides and HA forecast response conversions.
- Missing or expired required data never silently produces a suitable window or dry-weather event.
- HACS/hassfest, lint, localization and docs validation pass; version metadata consistent.
- Changelog distinguishes corrected outputs, new features, model relearning and compatibility changes.

### v2.14.0 additional

- Polar day/night (both hemispheres), DST repeated/skipped hours, midnight rollover, long provider outages.
- Rain-counter resets, missing-rain recovery without false stopped/started events, interrupted storage writes.
- No schema or learned-state change; no downgrade restriction. (The one-time calibration-bias reset adds one optional field with a default to the learning state as a marker; the schema version does not change and old stored data loads unchanged. This is verified by a test.) The file-level plan is [v2.14.0-coding-plan.md](v2.14.0-coding-plan.md).
- Regression tests for climatology window length, nowcast lead-time blending with sparse hourly rows, Open-Meteo elevation handling and bias reset, the midnight solar-energy gap, throttled Blitzortung discovery, the service/number range match, forecast-tile padding and AWEKAS log redaction.

### v3.0.0 additional

- Sparse forecasts and provider outages across midnight and beyond the forecast horizon.
- Multi-station isolation, source renames, interrupted storage writes.
- Upgrade tests preserving entity IDs, unique IDs and history, deterministically repairing affected models; pre-migration backup verified.
- Window transition tests prevent duplicate events and excessive state updates; coalescing tests cover tick-versus-pending-refresh and cancellation on stop.
- Pattern migration tests: standardizer slots and weights reset only for the four masked features and `dp_3h`, in only the models that use them; **every other stored value (remaining weights, standardizer slots, base rates, conditional rates, history entries) is byte-for-byte unchanged**; replay/live feature equivalence holds; a per-feature reset is compared with a per-target relearn on held-out history; and downgrade tolerance is verified.
- **Performance:** under a realistic source-burst replay, p95 compute time per update and state writes per burst are each no worse than the M0 baseline plus 10 percent, unless a documented feature justifies the difference. Thresholds are confirmed once the M0 baseline is measured.
- Authoritative scientific examples for every corrected formula, plus held-out, time-ordered evaluation for any claim of improved forecast skill. Synthetic scenarios validate behavior, not real-world accuracy.
- Dashboard and blueprint validation; entity count per default install does not grow beyond the documented budget.

Publishing, tagging, merging and deploying are outside this planning task and have not been performed. Per the release process, bump `manifest.json` before tagging each release.

| 1 | **Room ventilation advisor** (moved from v3.0) | Per-room dew point and moist-air enthalpy with documented pressure assumptions; wet-bulb/psychrometric validation from scope B; outdoor-condition, CO2, rain, wind and optional AQI/pollen inputs; states `recommended`, `limited`, `not_recommended`, `unknown` with separate purpose and blocker codes; hysteresis; logical device per named room that preserves entity IDs, unique IDs and user customizations; no indoor-temperature or mold prediction without a validated room model |
| 2 | **Persistent garden water balance** | Validated ET0 (scope B), per-zone crop coefficient, effective rainfall, storage limits and recorded irrigation; water units, resets, drainage and restart behavior; `record_irrigation` with duplicate-event protection; start with advice and specialist-controller integration |
| 3 | **Official warning adapters** | Named adapters for selected existing HA integrations with severity/onset/expiry mappings; no assumed universal alert schema; feed warnings into explanations and window restrictions |
| 4 | **PWS analytics** | Timestamped 24h/7d wind roses, calm fraction, consistent frequency/speed summaries; optional reports |
| 5 | **Better window presentation and profiles** | Calendar display, provider-supported 48h horizons, additional profiles only when inputs and validation exist |
| 6 | **Targeted Repairs flows** | Guided source remapping and prerequisite resolution, built on stable v3.0 diagnostics |

Higher-risk candidates to evaluate for later:

- Multi-provider scoring and blending by variable and lead time, with fair verification and API budgets.
- Source failover/fusion with provenance. Do not automatically choose the minimum thermometer reading; do not switch cumulative rain counters without a continuity model.
- Surface condensation/mold advice with explicit cold-bridge calibration or surface measurements.
- Broader device/subentry organization after room-device migration is proven.
- PV-array forecasting and panel diagnostics only if there is a clear benefit over existing specialist integrations.

The v3.1 headline is chosen after v3.0 feedback. Ventilation and water balance are the leading candidates; if water balance is selected, its scope B prerequisites (ET0 radiation, anemometer height, soil assumptions) must have passed validation first.

## Review corrections carried into this plan

- Valid HA native forecast fields must not be replaced with incorrect plain-field equivalents.
- Pirate Weather's `precipAccumulation` is in centimetres with mixed-phase semantics, not simply snow-only. Verify the response version and suitable liquid-equivalent fields.
- Open-Meteo elevation downscaling must be accounted for when assessing pressure mismatch.
- The freeze-unit defect must be tested for explicit overrides; ordinary auto imperial mode already consults HA units.
- Placeholder measurements and availability flags need separate treatment in learning; do not blindly mask every related feature without replay/live equivalence tests.
- Conservative Brier-based weights and below-air globe-temperature estimates are not, by themselves, proof of a bug. Validate model assumptions and domains before replacing them.
- Do not label the release "Platinum" merely because it uses newer HA APIs.
