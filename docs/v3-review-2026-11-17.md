# Weather Station Core: latest-code review and v3 proposal

> Review prepared using the code-review and [ha-integration-dev skill](https://github.com/tonylofgren/aurora-smart-home).

Reviewed on 17 November 2026 against **main, 2.13.17, commit 915cf667594207bacb0edd5e1ba009b028dce0bf**. The original working branch was `fix/issue191-pattern-learning-progress`, commit `4b9bc27`, version 2.13.14. Findings below were rechecked against the 2.13.17 snapshot. No integration source was changed during the audit.

**Recommendation:** make v3 a weather decision engine: useful time windows and room ventilation advice, with explicit freshness, provenance and reasons. The existing calculations, local learning, room mappings and forecast adapters provide most of the ingredients. A larger sensor catalogue would deliver less value than making those ingredients work together reliably.

**Scope and confidence**

This is a targeted deep review of setup/unload, source normalization, calculation orchestration, persistence/backfill, learning, forecast adapters, weather/sensor/event entities, options/actions, diagnostics, uploads and testing. It is not a line-by-line scientific certification of every formula or a live hardware/network qualification. Peer comparisons use maintainer documentation plus selected source files, not exhaustive audits of those projects.

Six defects were reproduced directly by calling the 2.13.17 implementation with controlled inputs during the review before regression tests were written.

The isolated synchronous suites for algorithms, coordinator, source freshness and sampling passed **261 tests**; the weather platform's synchronous subset passed **7**, with two async tests deselected. The normal full-suite invocation failed before collection because the HA test plugin imports `fcntl`, unavailable on Windows. Plugin-disabled broad runs were incomplete, included a registry-contract failure, and were stopped. They must not be represented as a passing full suite. Run the normal Linux HA matrix before releasing fixes.

The time-zone shift initially seen in the older checkout was fixed in 2.13.15 and is **not** an outstanding finding here. The latest condition hold, Windy v2 upload and recorder statistics unit fixes were also taken into account.

**Confirmed defects, in priority order**

1. **P1 — Cloud forecast expiry does not protect the adaptive rain estimate.** In `coordinator.py:2388–2397`, `_compute_rain_probability` takes precipitation probability from the first cached daily row without checking its date or the last successful fetch. A forecast dated 1 November still supplies 100% to the blend on 17 November. `_compute` also republishes cached cloud datasets without a shared freshness policy; daily forecast output does not exclude expired dates. A healthy local station therefore does not imply fresh forecast inputs. Fix with explicit issuance/retrieval/validity times, an expiry policy per product, and a local-only fallback when forecast input expires. Use the dedicated precipitation nowcast's existing stale-data behavior as a starting point. Add outage tests across midnight and beyond the forecast horizon. [Source](https://github.com/kmich/ha_ws_core/blob/915cf667594207bacb0edd5e1ba009b028dce0bf/custom_components/ws_core/coordinator.py#L2388).

2. **P1 — Soil moisture conversion can invert the irrigation conclusion.** `coordinator.py:1823` treats every value at or below 1 as a volumetric fraction, regardless of the source's unit. A real 1% reading becomes 100%; 0.5% becomes 50%. At 1.1%, it suddenly becomes 1.1%, introducing a discontinuity. Fix by reading the unit and exposing an explicit fraction/percentage setting when the source is ambiguous. Separately, `_compute_soil` assumes 40% field capacity for every probe and soil. Relative probe percentages are not automatically volumetric water content. That assumption needs configuration or a clearly limited heuristic label. [Source](https://github.com/kmich/ha_ws_core/blob/915cf667594207bacb0edd5e1ba009b028dce0bf/custom_components/ws_core/coordinator.py#L1820).

3. **P2 — Forecast retry backoff is not based on the last attempt.** `_get_cached_or_schedule_forecast` only checks delay when both cache and last successful fetch exist. Failed attempts increment a counter but do not advance the timestamp. With no successful cache and five prior failures, three invocations two seconds apart schedule three requests. With an old successful cache, retry age is still measured from that old success, so the intended delay can already have elapsed. Every source change can trigger this path. Track `last_attempt` or `next_retry_at` independently of `last_success`; reset the in-flight flag in `finally`, and test cold-start failure and failure after cache expiry. [Source](https://github.com/kmich/ha_ws_core/blob/915cf667594207bacb0edd5e1ba009b028dce0bf/custom_components/ws_core/coordinator.py#L5089).

4. **P2 — Local nowcast blending applies to the first three rows, regardless of lead time.** The updated weather platform removes past rows, then uses a row counter to decide which forecast points receive local observations. A single forecast for tomorrow noon, with forecast temperature 0°C and current temperature 30°C, becomes 21°C. This affects sparse, delayed or truncated provider forecasts. Determine weights from elapsed time to each valid timestamp and apply them only inside the intended 0–2 hour window. Keep all timestamp comparisons aware; a future internal UTC contract would also preserve repeated hours during daylight-saving transitions. [Source](https://github.com/kmich/ha_ws_core/blob/915cf667594207bacb0edd5e1ba009b028dce0bf/custom_components/ws_core/weather.py#L372).

5. **P2 — Missing rain input emits a false rain-stopped event.** `WSRainEvent.check_and_fire` converts missing or null rain rate into zero. After a positive rate, an empty observation fires `stopped`; the coordinator can produce this missing key when the mapped gauge becomes unavailable. Missing data should suspend transition detection, not establish dry weather. Define how state resumes after an outage so recovery cannot invent a second onset either. [Source](https://github.com/kmich/ha_ws_core/blob/915cf667594207bacb0edd5e1ba009b028dce0bf/custom_components/ws_core/event.py#L96).

6. **P2 — Failed unload still stops the coordinator.** `async_unload_entry` awaits `async_stop()` even when `async_unload_platforms` returns false. The reproduction returns false but records one coordinator stop. HA can retain entities while their listeners and schedules have been stopped. Return false before teardown if platform unload fails; test both outcomes. Also audit task ownership: the forecast and sea-temperature tasks use bare `hass.async_create_task`, unlike the tracked `_spawn` jobs, so their cancellation is not covered by `_unsubs`. [Source](https://github.com/kmich/ha_ws_core/blob/915cf667594207bacb0edd5e1ba009b028dce0bf/custom_components/ws_core/__init__.py#L409).

**Architecture and scientific interpretation**

| Dimension | Assessment | Implication |
|---|---|---|
| Correctness | Needs fixes before expanding automation advice | Unknown, stale, forecast and observed values need consistent semantics |
| Maintainability | High concentration of responsibilities | The roughly 6,000-line coordinator owns scheduling, networking, history, physics, quality, learning and presentation |
| Performance | Structural risk; no live benchmark performed | Every watched source change runs the complete calculation pipeline and publishes updates |
| Security/privacy | Good foundations, incomplete audit | HTTPS and recursive diagnostics redaction are present; no exploit was established in this review |
| Testing | Broad unit coverage, important boundary gaps | Existing passing tests missed the six reproduced cases; HA lifecycle and failure-path tests need emphasis |

There is substantial good engineering here: entity IDs preserve station identity; runtime data belongs to entries; the provider adapters have a common interface; persistent learning is separated from history; recorder recovery handles boundaries; the sampling distinction prevents high-frequency source updates from advancing all learning state; diagnostics redact credentials and configured location fields. Pattern Forecast already has prequential scoring, baselines, historical warm-up, target-specific maturity and degradation. Those are strengths to retain.

Freshness is uneven. Source health can report stale measurements after calculations have already consumed their numeric values. Pattern Forecast has extra input-quality screening, but that does not automatically protect every ordinary derived sensor or consumer. Introduce quality at the input boundary and propagate it by dependency: stale wind should affect wind-dependent outputs, not unrelated humidity outputs.

Do not conflate station calibration with local forecast correction. The optional automatic calibration currently adjusts observation offsets toward a regional model reference. Persistent disagreement can reflect a real microclimate, elevation or exposure difference. For a product emphasizing local weather, retain raw and manually calibrated observations, and learn model bias in a separate forecast layer. This is a design/scientific recommendation, not proof of a numerical defect in the bounded adjustment code.

The learning engine's maturity is not a calibrated confidence interval. A model can beat climatology while individual probabilities remain imperfectly calibrated. Preserve separate fields for data quality, model maturity, forecast probability and any empirically validated uncertainty. Add reliability plots and time-ordered evaluation before claiming quantified confidence.

**A substantial, bounded v3**

The promise should be: **“Your station tells you when conditions suit what you want to do, explains why, and tells you when it lacks enough reliable data.”**

Ship three connected capabilities:

1. **Weather windows.** Configure a small number of profiles with measurable constraints and a required duration. Start with outdoor drying and garden work: rain amount/probability, wind/gust, temperature, humidity and daylight. Return suitable intervals and rejection reasons for the next 24 hours. Let users customize limits. A result might say “14:00–16:00 meets your limits; after 16:00 forecast gusts exceed your threshold.” Keep the current observed state distinct from predicted future suitability.
2. **Room ventilation decisions.** Reuse named rooms to compare indoor and outdoor moisture, cooling potential and CO₂ demand. Combine with current rain/wind and optional air quality/pollen limits. Expose `recommended`, `limited`, `not_recommended` and `unknown`, with explicit reasons. Do not infer a future room temperature without a validated room model. Initial functionality can assess current ventilation and forecast outdoor opportunities separately.
3. **A shared quality and explanation contract.** Every decision records the input sources, observation age, forecast validity, missing inputs, evaluated limits and local-model maturity where relevant. Consumers can distinguish “conditions do not meet your limits” from “we cannot assess them.” Reuse this contract in entities, a response-returning action and a compact dashboard.

Expose `ws_core.get_weather_windows` as a response action with `profile_id`, `start`, `end`, `suitability`, `reason_codes`, `evaluated_at` and source-quality details. A calendar can be added for convenient display; response data should be the core API. Keep profile status and next-start entities small, with detailed interval data returned on demand to avoid recorder growth.

This can run with deterministic calculations. It does not require an LLM or a new cloud dependency. Offline mode should provide current local advice; unavailable forecast horizons should explicitly remain unknown. Automations can consume the advice; direct control of valves, windows and awnings is outside the first v3 scope.

**Implementation sequence and release gates**

First, ship the confirmed reliability fixes separately in v2.13.x. Include regression cases for cold-start retries, expired forecasts, missing rain, percent/fraction moisture and failed unload. Do not make users wait for v3 to receive them.

Next, extract boundaries incrementally: source observations and quality; forecast retrieval/cache/validity; accumulated history; pure derived calculations; decision profiles. Preserve existing entity unique IDs, config entries and stored learning. Move one subsystem at a time with replay comparisons; avoid a wholesale coordinator rewrite.

Then build one vertical slice: a drying-window profile, structured response, next-window entity, explanation view and blueprint. Add ventilation using the same quality contract. Only then broaden profiles.

Before the v3 release, require:

- Linux tests on the declared minimum and current supported HA versions, with real setup/unload/reload coverage.
- UTC/DST tests, sparse forecasts, midnight rollover, source renames, restarts and multi-station isolation.
- Missing or expired required input always produces unknown/limited advice, never a fabricated safe state.
- Stable profiles and window identifiers; unchanged inputs do not repeatedly fire transitions.
- Compatibility tests preserving current entity IDs, history and learned state on upgrade and option changes.
- A measured compute/state-write budget under realistic station update rates; no unrelated network request on source events.
- Scenario replay for decisions, plus recorded-data evaluation for any claims of forecast improvement. Synthetic tests establish behavior, not real-world forecast skill.
- A dashboard showing the decision, time window and reasons before exposing detailed indices.

The key product choice is to combine the integration's existing depth into a small set of useful, testable decisions. That gives v3 a clear purpose while keeping specialist irrigation control and large forecast ensembles out of the critical path.
